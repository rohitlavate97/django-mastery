# Django Cache Framework

## 1. Mental Model
```text
Django Framework Levels of Caching:

[Level 1: Site-Wide Cache] -> Caches entire HTTP responses (Middleware)
        |
[Level 2: Per-View Cache] -> Caches specific view responses (@cache_page)
        |
[Level 3: Template Fragment] -> Caches parts of a template ({% cache %})
        |
[Level 4: Low-Level API] -> Caches specific Python objects/data (cache.get/set)
```

## 2. Why It Exists
Different parts of an application require different caching granularity. A static "About Us" page can be cached entirely (Site-Wide). A user dashboard cannot be cached entirely, but the complex analytics sidebar can be (Template Fragment).

## 3. Internal Working
Django abstracts the underlying caching engine (Redis, Memcached, File) behind a unified API (`django.core.cache`). 
- **Site-Wide/View caching** utilizes the `UpdateCacheMiddleware` (to save the response) and `FetchFromCacheMiddleware` (to serve the response before view execution).
- **Cache Keys** are generated by hashing the URL, request method, and query parameters.

## 4. Basic Implementation
**Per-View Caching:**
```python
# views.py
from django.views.decorators.cache import cache_page

@cache_page(60 * 15) # Cache for 15 minutes
def product_catalog(request):
    # This expensive logic only runs once every 15 minutes
    products = Product.objects.all().prefetch_related('categories')
    return render(request, 'catalog.html', {'products': products})
```

**Low-Level API:**
```python
from django.core.cache import cache

def get_expensive_calculation():
    return cache.get_or_set('my_calc_key', perform_calculation, timeout=300)
```

## 5. Production-Ready Implementation
Template fragment caching with dynamic versioning based on object state.

```html
<!-- template.html -->
{% load cache %}

<!-- Cache this specific sidebar for 1 hour, uniquely identified by user.id and the user's last login timestamp -->
{% cache 3600 sidebar user.id user.last_login %}
    <div class="sidebar">
        <!-- Expensive queries inside -->
        <h3>Your Recent Activity</h3>
        {% for activity in user.get_recent_activity %}
            <p>{{ activity }}</p>
        {% endfor %}
    </div>
{% endcache %}
```
*Why this is production-ready:* By appending `user.last_login` to the cache tag, the cache automatically invalidates itself whenever the user logs in again, without needing explicit `cache.delete()` calls in python code.

## 6. Anti-Patterns
🔴 **Ticking Time Bomb:**
```python
# Using @cache_page on a view that handles POST requests or user-specific data
@cache_page(3600)
def user_profile(request):
    return render(request, 'profile.html', {'user': request.user})
```
*Why it's bad:* `cache_page` uses the URL as the cache key. If User A visits `/profile/`, their private data is cached. When User B visits `/profile/`, they will see User A's data! You must use the `Vary` header (e.g., `Vary: Cookie`) to cache per-user, but this often leads to cache exhaustion.

## 7. Environment-Specific Behavior
| Level | Local | Production |
|-------|-------|------------|
| Site-Wide | Hard to test | Rarely used (use CDN/Cloudflare instead) |
| Low-Level | `LocMemCache` | `RedisCache` |

## 8. Local Development Issues
🔴 SYMPTOM: You change code, but the view still returns old data.
🔍 CAUSE: `@cache_page` is active, and you are using `LocMemCache` which persists across requests in the local dev server until restart.
🔧 FIX: Set `CACHES['default']['BACKEND'] = 'django.core.cache.backends.dummy.DummyCache'` in your local settings to bypass caching entirely during development.

## 9. Production Issues
🔴 INCIDENT: Unintentional Data Leak
- **Severity:** CRITICAL
- **Investigation:** Users reported seeing other users' shopping carts.
- **Root Cause:** A developer used `@cache_page` on the checkout view. The cache key did not account for session cookies.
- **Fix:** Removed `@cache_page` from authenticated views. Moved to Low-Level API to cache only the product data, not the user-specific cart data.

## 10. Failure Simulation
Apply `@cache_page` to a view. Start your server, load the page, then shut down your Redis server. Refresh the page. Django will throw a 500 error by default. This proves you need error handling or `django-redis` configurations to ignore connection errors (`IGNORE_EXCEPTIONS = True`).

## 11. Decision Matrix
| Feature | When to Use | Alternative |
|---------|-------------|-------------|
| Site-Wide | Almost Never | Cloudflare / Fastly (Edge Caching) |
| `@cache_page` | Anonymous, public pages (Blogs) | Low-Level Cache |
| `{% cache %}` | Expensive template rendering | Low-Level Cache |
| Low-Level API | 95% of use cases, fine-grained control | - |

## 12. Senior-Level Questions
**Q: How do you bypass the cache for an admin user while using `@cache_page`?**
A: You cannot easily do this with the standard decorator. You must write a custom decorator or middleware that inspects `request.user.is_staff` and dynamically decides whether to read/write to the cache.

## 13. Production Checklist
- [ ] `@cache_page` is NEVER used on views that render user-specific or sensitive data.
- [ ] Local development uses `DummyCache` to prevent debugging headaches.
- [ ] Template fragment caches use state-based variables (like timestamps) for automatic invalidation.
