## 2. Source Code Reading Exercises

Do not treat Django as a black box. Open the source code (e.g., clone the repo on GitHub) and trace the execution.

### Exercise 2.1: The Request Lifecycle
**Goal:** Trace a request from the WSGI server to the View.
1. Open `django/core/handlers/wsgi.py`. Find the `WSGIHandler.__call__` method.
2. Track how the `environ` dict is converted to an `WSGIRequest` object.
3. Follow the execution to `django/core/handlers/base.py` -> `BaseHandler.get_response`.
4. Observe the exact loop where middleware is applied.
**Deliverable:** Write a 1-page summary or draw an ASCII diagram of the execution path.

### Exercise 2.2: ORM Query Construction
**Goal:** Understand how `User.objects.filter(name='John')` becomes SQL.
1. Start at `django/db/models/manager.py`. Trace `.filter()`.
2. Follow it down to `django/db/models/query.py` (`QuerySet.filter`).
3. Notice it calls `self.query.add_q()`. Look at `django/db/models/sql/query.py`.
4. See how the AST (Abstract Syntax Tree) is built before any database connection is made.
**Deliverable:** Explain to a colleague why `QuerySet` evaluation is lazy based on your code tracing.

## 3. Debugging Challenges (The "Break It" Labs)

Create a blank Django project and intentionally induce these failures.

### Lab 3.1: The Silent Memory Killer
**Setup:** Create a model with 5 fields. Insert 500,000 rows.
**Task:** Write a view that iterates over all rows: `for obj in Model.objects.all(): pass`.
**Observe:** Monitor your OS memory usage. Watch it spike.
**Fix:** Rewrite the view to process the data without exceeding 50MB of RAM. (Hint: `iterator(chunk_size=...)` or `values_list`).

### Lab 3.2: The Deadlock
**Setup:** Use PostgreSQL. Create a `BankAccount` model.
**Task:** Write a management command that starts a transaction, updates Account A, sleeps for 5 seconds, then updates Account B. Write a second command that starts a transaction, updates Account B, sleeps, then updates Account A. Run both simultaneously in two terminal windows.
**Observe:** Watch PostgreSQL detect the deadlock and kill one of the transactions. Look at the Django traceback.
**Fix:** Refactor the logic to acquire locks in a consistent, deterministic order.

### Lab 3.3: The Connection Pool Exhaustion
**Setup:** Configure `CONN_MAX_AGE` to `0` (the default). Use JMeter or Apache Bench to send 200 concurrent requests to a view that does a `time.sleep(2)` and a database query.
**Observe:** Watch your database connections spike, leading to `OperationalError: FATAL: remaining connection slots are reserved...`
**Fix:** Implement connection pooling (PgBouncer) or tune Gunicorn worker counts and timeout settings.

## 4. Production Simulation Exercises

A master knows how code behaves in a harsh environment.

### Exercise 4.1: The Zero-Downtime Migration
**Scenario:** You have a table with 10 million rows. You need to change a `CharField(max_length=50)` to `max_length=100`.
**Challenge:** Standard `makemigrations` and `migrate` will lock the table in PostgreSQL, causing downtime.
**Execution:** Perform this migration on a live database undergoing heavy read/write load (simulate with a load testing script) without dropping a single HTTP request.
**Skills Required:** Understanding Postgres table locks, transaction handling in migrations, and multi-step deployments.

### Exercise 4.2: The Cache Stampede
**Scenario:** A heavily trafficked endpoint caches an expensive database aggregation for 5 minutes.
**Challenge:** When the cache expires at minute 5, 1,000 concurrent requests hit the view simultaneously. They all miss the cache and hit the database at the exact same millisecond. The database CPU spikes to 100% and crashes.
**Execution:** Implement a locking mechanism (using Redis) to ensure only *one* worker computes the aggregation while the other 999 workers serve stale data or wait.

## 5. System Design Exercises (Whiteboard/Architecture)

Designing systems *around* Django is as important as designing *within* Django.

### Exercise 5.1: The Webhook Processor
**Prompt:** Design a Django system that receives 10,000 webhooks per second from Stripe. You must not lose a single event, and you must respond with a `200 OK` within 200ms, but processing the event takes 2 seconds.
**Key Concepts to Demonstrate:** API Gateway, Message Queues (Celery/RabbitMQ/Kafka), Idempotency keys, database write optimization.

### Exercise 5.2: The Global Edge
**Prompt:** Your Django app is currently in `us-east-1` (Virginia). Users in Sydney, Australia are experiencing 800ms page loads due to latency.
**Challenge:** Architect a solution using Django to drop latency for Sydney users below 100ms.
**Key Concepts to Demonstrate:** Content Delivery Networks (CDNs), Read-Replicas, edge caching, database routing (`DATABASE_ROUTERS`), dealing with replication lag.

## 2. Django Internal Source Traces

Let's dive into how Deliberate Practice actually works under the hood in Django 6.1+.

```python
# Django Internal Trace (Conceptual representation)
# Location: django/core/handlers/base.py

class BaseHandler:
    def get_response(self, request):
        # 1. Resolve URL
        resolver_match = self.resolve_request(request)
        
        # 2. Apply Middleware
        response = self._middleware_chain(request)
        
        # 3. Execute View
        if response is None:
            response = resolver_match.func(request, *resolver_match.args, **resolver_match.kwargs)
            
        return response
```
*Notice how the execution flows from the base handler through the middleware chain down to the view layer.*

## 3. Basic vs Production-Ready Implementation

### Naive Implementation (Anti-Pattern)
```python
# TICKING TIME BOMB: Do not use in production
def basic_approach(request):
    data = do_something_expensive()
    return HttpResponse(data)
```

### Production-Hardened Implementation
```python
import logging
from django.core.cache import cache
from django.http import JsonResponse

logger = logging.getLogger(__name__)

def production_ready_approach(request):
    try:
        # 1. Check Cache
        cache_key = f"data_{request.user.id}"
        data = cache.get(cache_key)
        
        if not data:
            # 2. Perform Operation with Timeout
            data = do_something_expensive(timeout=2.0)
            cache.set(cache_key, data, timeout=300)
            
        return JsonResponse({"status": "success", "data": data})
        
    except Exception as e:
        logger.error(f"Failed to process request: {str(e)}", exc_info=True)
        return JsonResponse({"status": "error", "message": "Internal Server Error"}, status=500)
```

## 5. 3:00 AM Production Incident: Deliberate Practice Failure

🔴 **SYMPTOM**: At 3:15 AM on Black Friday, p99 latency spiked to 15s. HTTP 502 Bad Gateway errors spiked to 4%.

🔍 **CAUSE**: Connection pool exhaustion due to a slow query locking the main thread.

**Timeline:**
- 03:00 AM: Traffic increased by 400%
- 03:10 AM: Database CPU hit 95%
- 03:15 AM: Gunicorn workers starved, queuing requests

🔧 **DEBUG & FIX**:
```bash
# Debugging commands used
$ tail -f /var/log/nginx/error.log
$ htop
$ psql -c "SELECT * FROM pg_stat_activity WHERE state = 'active';"
```

**Permanent Fix**:
Implemented pgbouncer for connection pooling and added a 2-second statement timeout to PostgreSQL.
